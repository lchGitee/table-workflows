# 新建任务模板

本流程把一次人工完成的表格任务沉淀为可重复执行的任务模板。重点是获得可运行、可验证的产物，不是写一份看起来合理的规则说明。

## 1. 收集材料并确认角色

最低需要：

- 一张或多张源表；
- 与这些源表对应、经过人工确认的正确结果表。

结果表可以同时提供目标结构。若未来每次都要填写另一份空白表，再收集空白结果模板。用户可以分批上传；每批上传后列出已识别的文件角色和仍缺少的材料。

开始分析前确认：

- 这项任务最终要得到什么结果；
- 每个文件是源表、人工正确结果还是空白结果模板；
- 多张源表是不同数据角色，还是同一角色的多份文件；
- 历史源表和人工结果是否属于同一业务周期或同一批数据；
- 用户希望给任务模板起什么名字。用户没有名称时可以建议一个简短名称并让其确认。

文件角色、业务周期或目标不明确时暂停规则推断。不要根据文件名直接认定。

## 2. 建立结构事实

使用当前环境可用的本地表格工具或库检查文件，至少记录：

- 文件类型、工作表名称和可见性；
- 表头、数据区域、记录数量和主要字段类型；
- 可能的唯一键、复合键、重复键和跨表关联键；
- 公式、合并单元格、隐藏行列、命名区域和需要保留的对象；
- 结果表中可能由源表解释的区域、固定内容、公式区域和人工填写区域；
- 结构歧义、异常数据和不受当前工具支持的工作簿特性。

结构指纹应基于结构描述，而不是整个文件的字节哈希。业务月份、普通数据值或文件名变化不应必然导致结构不兼容。为每个输入角色和需要校验的结果模板定义同一套规范化提取规则，把从历史样本实际提取的结构描述保存到版本目录，并用该描述的规范化序列计算期望指纹。运行时必须从当期文件重新执行同一提取过程；读取已保存描述并计算其哈希只能证明依据文件未变，不能证明当期文件结构匹配。细节见 [任务模板协议](workflow-bundle.md#结构指纹)。

## 3. 从正确结果中发现候选关系

将结果拆成可验证的小关系，例如：

- 字段复制、改名和格式转换；
- 查找、关联、去重和优先级；
- 条件判断、映射和默认值；
- 计算、舍入、分组和汇总；
- 排序、分区、透视或固定模板回填；
- 无法从源表解释的人工结果。

区分三类信息：

- **结构事实**：可以由程序直接观察；
- **候选规则**：与历史结果一致，但仍可能只是偶然关系；
- **用户政策**：必须由用户说明或确认的业务选择。

不要用单个样本中的相关性冒充因果规则。多个候选都能解释结果时，展示最小差异并询问用户，而不是自行选择最复杂或覆盖最广的方案。

## 4. 只询问会改变结果的问题

优先询问以下歧义：

- 跨表使用哪个键关联，键缺失或重复时怎么办；
- 多条记录命中时取哪一条，是否需要排序或优先级；
- 空值、零值、错误值和未知值如何处理；
- 计算单位、舍入精度、日期边界和汇总范围；
- 哪些内容是一次性人工特例，哪些是长期政策；
- 哪些区域允许写入，哪些公式、格式和内容必须保持不变。

相关问题可以合并，但不要一次抛出完整技术问卷。用实际业务例子说明问题影响。

## 5. 生成可执行实现

先检查工作区是否已有可复用的表格运行时或项目约定，并遵循现有工具和风格。没有合适运行时时，再生成最小实现。

选择产物：

- 有现成、确定性的 DSL 运行器且所有规则都可表达：保存 DSL 和固定运行方式；
- 其他情况：生成脚本；
- DSL 无运行器：同时生成最小运行器，或者改用脚本；
- 仅有自然语言规则说明：只能作为文档，不能算完成。

实现必须：

- 从运行请求文件读取本次输入路径、结果模板路径、参数和输出路径；
- 对每个实际输入和结果模板重新提取规范化结构、计算观察指纹，并在读取业务数据前与期望指纹或明确兼容条件比较；
- 对结构描述中声明的工作表、表头、公式、合并、隐藏、命名区域和对象等特征逐项执行可观察的校验；当前工具无法可靠观察的契约字段必须标为未支持并停止，不能默认视为匹配；
- 只产生声明范围内的结果；
- 对关键歧义失败关闭，不静默吞错或猜测；
- 不覆盖任何输入文件；
- 在相同输入、版本和环境下产生相同业务结果；
- 将依赖、入口命令和执行文件校验值写入 `manifest.json`；使用非标准库、共享运行时或外部 DSL 运行器时，额外保存包含精确版本和可用完整性信息的机器可读依赖锁，将其列为 `DEPENDENCY_LOCK` 产物，并在每次运行前校验。外部路径或 `node_modules` 符号链接本身不是依赖锁。

运行请求格式和目录结构见 [任务模板协议](workflow-bundle.md)。

## 6. 用历史正确结果回放

使用历史源表执行新产物，并将输出与人工正确结果比较。验证至少包括：

- 只改变普通数据值或记录数量、结构不变的输入仍得到相同结构指纹判断；
- 至少一个只改变契约相关结构的负例会在创建输出前阻断。对于工作簿，至少覆盖一个非表头结构变化，例如工作表可见性、隐藏行列、合并区域、命名区域或绘图对象，避免实现退化为只检查表头；
- 声明输出区域中的值是否一致；
- 公式、样式和必须保留的工作簿对象是否仍然存在；
- 声明区域以外是否出现非预期修改；
- 记录数量、唯一性、汇总平衡和用户确认的业务不变量是否成立；
- 输出能否被目标表格软件重新打开。

结构稳定性和漂移负例必须真实执行，并在报告中记录输入变体、预期结果、实际退出状态以及是否产生输出。仅检查代码或再次哈希保存的结构依据，不能算通过。

所有差异都必须进入以下一种结果：

- 修正规则后重新回放；
- 用户确认是人工正确结果中的错误；
- 用户确认是允许差异，并记录范围、原因和确认；
- 尚未解决，因此版本不能通过。

不要只报告“脚本执行成功”。执行成功不等于结果正确。

## 7. 保存和交付

按照 [任务模板协议](workflow-bundle.md) 创建新目录和 `manifest.json`。不要把任何用户规则写回 Skill 目录。

状态规则：

- 没有可通过的历史正确案例：`DRAFT`；
- 至少一个历史正确案例回放通过：`TRIAL`；
- 至少一个未参与最初规则发现的独立案例也通过，且没有阻断项：可以标记为 `VALIDATED`；
- 结构或实现发生未解决变化：`NEEDS_REVIEW`。

完成时用普通话告诉用户：

- 任务模板名称和保存位置；
- 当前版本和状态；
- 使用了脚本还是 DSL；
- 已通过哪些历史案例；
- 仍有哪些限制；
- 下次需要上传哪些文件以及如何调用。

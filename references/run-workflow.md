# 运行任务模板

正常运行的目标是重复执行已经验证过的固定版本。此模式不重新发现规则，也不修改实现。

## 1. 选择任务模板

用户明确给出任务模板名称或目录时，优先读取对应 `manifest.json`。否则只在当前工作区约定的 `.table-workflows/` 中查找候选。

候选匹配顺序：

1. 用户明确选择的任务模板；
2. 输入角色数量和文件类型；
3. 各输入的结构指纹；
4. 结果模板的结构指纹；
5. manifest 中明确声明的兼容条件。

不要只根据文件名、最近使用时间或业务描述自动选择。没有可靠候选时建议新建任务模板；多个可靠候选时让用户选择。

## 2. 收集本次文件

根据 `inputSlots` 逐项检查用户已上传的文件，只请求缺少的角色。向用户展示简单的角色清单，不暴露内部路径或结构 JSON。

如果目标模式要求用户每次提供结果模板，确认本次结果模板；如果任务模板保存了可复用模板，则从它创建副本。任何情况下都不得把历史人工正确结果直接当作可覆盖文件。

## 3. 运行前验证

执行前必须确认：

- `manifest.json` 符合当前支持的协议版本；
- 当前版本状态不是 `DRAFT`、`NEEDS_REVIEW` 或 `RETIRED`；
- 入口文件和所有执行产物的 SHA-256 与 manifest 一致；
- 所需运行时和依赖可用；存在 `DEPENDENCY_LOCK` 时，当前运行时、非标准库和外部运行器的精确版本及完整性信息与锁文件一致；
- 每个输入角色完整，并且从本次实际文件重新提取的规范化结构及观察指纹匹配期望值或符合明确的兼容条件；
- 目标模板匹配，输出路径与所有输入路径不同；
- 输出目录可写，且不会覆盖已有文件。

依赖缺失时说明缺少什么。安装依赖、访问网络或修改系统环境仍需遵循当前 Agent 的授权边界。

结构比较必须使用保存 `basis` 时的同一套提取字段、规范化和序列化规则。不得把 `basis` 文件自身的哈希当作本次输入的观察指纹，也不得因为当前工具读不到某个契约字段就跳过该字段并宣称匹配。结构提取或依赖校验失败时，在读取业务数据和创建输出前停止。

如果实现文件校验值变化，视为未审核修改并进入优化模式，不能在正常运行中自动更新校验值。

## 4. 构造并执行运行请求

按照 [任务模板协议](workflow-bundle.md) 创建本次 `run-request.json`，将每个输入文件绑定到明确的 `slotId`。使用 manifest 中保存的参数数组运行命令，不拼接成可由 shell 再解释的字符串。

正常运行中：

- 不生成新脚本或 DSL；
- 不修改当前版本文件；
- 不更改长期规则；
- 不因新数据无法匹配而引入默认兜底；
- 不让模型逐格决定业务输出。

## 5. 验证结果

运行后执行 manifest 声明的阻断检查和警告检查，至少确认：

- 输出文件存在且可以重新打开；
- 输出结构仍与目标契约一致；
- 禁止区域没有变化；
- 记录数、唯一性、汇总平衡等业务不变量通过；
- 实现没有报告未识别输入、跳过记录或未处理异常；
- 结果文件哈希、任务模板版本，以及每个实际输入和结果模板的观察结构指纹进入运行回执。

阻断检查失败时不得把文件描述为完成结果。保留诊断信息，建议用户进入优化模式。警告可以随草稿交付，但必须向用户说明影响范围。

## 6. 交付

向用户提供：

- 新生成的结果文件；
- 使用的任务模板名称与版本；
- 校验结论和异常数量；
- 是否仍需人工复核；
- 本次运行回执的位置。

运行回执可以保存指纹、计数、规则版本和异常摘要，默认不复制源表原文或敏感单元格值。

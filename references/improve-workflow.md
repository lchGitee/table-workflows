# 优化任务模板

优化模式处理人工纠错、业务政策变化、输入结构变化和结果模板变化。它可以生成新版本，但不能破坏当前可工作的版本。

## 1. 锚定问题

先确定：

- 哪个任务模板、版本和历史运行产生了问题；
- 用户提供的是单个错误说明、修正后的结果表，还是新结构样本；
- 期望结果与当前结果具体差在哪里；
- 问题来自数据异常、实现缺陷、长期政策变化还是模板结构变化。

能够用实际文件和运行回执定位时，不要求用户重新描述技术细节。

## 2. 确认影响范围

必须让用户区分：

- **仅本次处理**：只修正当前输出并写入本次运行回执，不修改任务模板；
- **以后都这样**：进入持久版本升级；
- **尚不确定**：保留为待复核案例，不扩大规则范围。

不要把一个单元格的纠正自动推广到整列、全部文件或所有未来数据。需要扩大作用范围时，用业务语言说明会影响哪些历史和未来情况。

## 3. 创建候选新版本

持久修改时：

1. 从当前有效版本复制出新的候选版本目录；
2. 保留旧版本，不原地覆盖；
3. 用最小改动修改脚本、DSL、运行器或结构契约；
4. 为新发现的长期行为增加可回放案例或明确不变量；
5. 更新执行产物校验值，但暂不切换 manifest 的当前版本；
6. 生成候选 manifest，并记录变更原因、用户确认和预期影响范围。

不要通过增加宽泛默认值、吞掉异常或跳过失败记录来让测试表面通过。

## 4. 回归验证

候选版本必须依次通过：

- 新纠错案例；
- 所有仍适用且可回放的历史正确案例；
- 输入和结果模板结构检查，包括从实际文件重新计算观察指纹；
- 数据变化但结构不变的稳定性用例，以及契约相关结构变化会在输出前阻断的负例；
- 非标准库、共享运行时或外部运行器的依赖锁校验；
- 禁止区域、公式、样式和工作簿完整性检查；
- manifest 中已有的阻断不变量。

历史案例与新政策确实冲突时，让用户确认政策生效边界，并把旧案例标记为“不再适用”及其原因；不要删除失败证据。

没有保存可回放历史案例时，可以交付候选版本，但状态最多为 `TRIAL`。不能仅凭当前修正样本升级为 `VALIDATED`。

## 5. 发布或保留候选

全部要求通过后：

- 递增版本号；
- 将候选 manifest 固化为新版本目录中的 `version-manifest.json`；
- 再用同一份内容更新根目录 `manifest.json`，切换当前入口和执行产物校验值；
- 更新验证时间、案例状态和变更摘要；
- 保留上一版本以便回滚；
- 根据验证证据设置 `TRIAL` 或 `VALIDATED`。

仍有阻断差异时，不切换当前有效版本。可以将候选保留为 `NEEDS_REVIEW`，并明确下一步还需要什么数据或决定。

## 6. 模板结构变化

先区分：

- 业务语义未变，只是可明确兼容的结构调整；
- 输出区域或字段含义改变，需要新版本；
- 已经成为不同业务流程，应新建任务模板。

兼容范围必须显式写入结构契约并由案例验证。不要把“忽略所有新增列”“自动选择最像的工作表”之类宽泛规则作为兼容策略。

完成时向用户说明旧版本是否仍可用、新版本验证了哪些案例、哪些输入会触发结构漂移，以及如何回滚。
